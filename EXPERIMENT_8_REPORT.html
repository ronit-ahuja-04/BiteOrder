3. Theory Questions

1. What is Docker and containerization?

Docker is an open platform for building, shipping and running applications in containers. Containerization packages an application together with its runtime, libraries and configuration into one standard unit (a container) that runs the same way on any machine that has a container engine. Containers are isolated processes that share the host operating-system kernel, so they start in seconds and are much smaller than virtual machines, which each carry a full guest operating system.

ContainerVirtual machine
PackagesApp + dependencies (no guest OS)Full guest OS + app
Size / start-upMegabytes / secondsGigabytes / minutes
IsolationProcess-level (shared kernel)Hardware-level (own kernel)
PortabilityRuns the same everywhere ("works on my machine" solved)Heavier to move

In this experiment BiteOrder runs as three containers: MongoDB, the API (247 MB image on disk) and the frontend served by nginx (77 MB).

2. What is Docker Compose?

Docker Compose is a tool for defining and running multi-container applications from one YAML file (docker-compose.yml). The file lists the services (containers), the images or build contexts, environment variables, ports, volumes, health checks and start-up order (depends_on). One command, docker compose up --build, builds the images and starts the entire stack on a shared network where the services reach each other by service name (for example the API connects to mongodb://mongo:27017).

3. What is a Dockerfile?

A Dockerfile is a text file with the instructions that Docker follows to build an image: FROM (base image), WORKDIR, COPY, RUN (execute a command while building), ENV/ARG (variables), EXPOSE (port), USER, HEALTHCHECK and CMD (command that starts the container). Each instruction creates a cached layer, so copying package.json and installing dependencies before copying the code makes rebuilds fast. A multi-stage Dockerfile builds in one stage and copies only the result into a small final image; the BiteOrder frontend uses this: Node builds the React bundle, and nginx serves the static files.

4. What is GitHub Actions?

GitHub Actions is the CI/CD service built into GitHub. A workflow is a YAML file in .github/workflows/ that runs on events such as a push or a pull request. It contains jobs that run on GitHub-hosted runners, and each job is a list of steps (shell commands or reusable actions such as actions/checkout). Jobs can have service containers (for example MongoDB) and can depend on each other with needs. The BiteOrder workflow tests the API, builds the frontend, builds both Docker images and then triggers the deployment, so broken code never reaches production.

4. Code

4.1 Backend Dockerfile – server/Dockerfile

# ---- BiteOrder API (Node.js + Express + Socket.IO) ----
FROM node:20-alpine

ENV NODE_ENV=production
WORKDIR /app

# Install only production dependencies first (better layer caching)
COPY package*.json ./
RUN npm ci --omit=dev

# Application code
COPY . .

# Run as the unprivileged "node" user
USER node

EXPOSE 5001
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD wget -qO- http://127.0.0.1:5001/health || exit 1

CMD ["node", "server.js"]

4.2 Frontend Dockerfile (multi-stage) and nginx – client/Dockerfile, client/nginx.conf

# ---- BiteOrder frontend (React + Vite + Tailwind) : build, then serve with nginx ----
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
# Public URL of the API, baked into the bundle at build time (Vite reads VITE_* variables)
ARG VITE_API_BASE=http://localhost:5001
ENV VITE_API_BASE=$VITE_API_BASE
RUN npm run build

FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
HEALTHCHECK --interval=30s --timeout=5s CMD wget -qO- http://127.0.0.1/ >/dev/null || exit 1
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  # Single-page app: unknown paths (/login, /admin ...) are handled by React Router
  location / {
    try_files $uri /index.html;
  }

  # Cache hashed build assets for a year
  location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }
}

4.5 GitHub Actions workflow – .github/workflows/ci.yml

name: CI / CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  server-tests:
    name: API tests (Node + MongoDB)
    runs-on: ubuntu-latest
    services:
      mongo:
        image: mongo:7
        ports: ["27017:27017"]
    defaults:
      run:
        working-directory: server
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: server/package-lock.json
      - run: npm ci
      - run: npm test
        env:
          TEST_MONGODB_URI: mongodb://localhost:27017/biteorder_test
          JWT_SECRET: ci_only_secret

  client-build:
    name: Frontend production build
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: client
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
          cache-dependency-path: client/package-lock.json
      - run: npm ci
      - run: npm run build
        env:
          VITE_API_BASE: https://example.invalid   # real value is set in Vercel
      - uses: actions/upload-artifact@v4
        with:
          name: client-dist
          path: client/dist

  docker-build:
    name: Docker images build
    runs-on: ubuntu-latest
    needs: [server-tests, client-build]
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t biteorder-api ./server
      - run: docker build -t biteorder-web ./client

  deploy:
    name: Deploy (Render API + Vercel frontend)
    runs-on: ubuntu-latest
    needs: [docker-build]
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    steps:
      # Backend: Render builds from the Dockerfile; a deploy hook triggers it right after the checks pass.
      - name: Trigger Render deploy
        env:
          RENDER_DEPLOY_HOOK: ${{ secrets.RENDER_DEPLOY_HOOK }}
        run: |
          if [ -n "$RENDER_DEPLOY_HOOK" ]; then curl -fsS "$RENDER_DEPLOY_HOOK" && echo "Render deploy triggered"; else echo "RENDER_DEPLOY_HOOK not set - skipping"; fi
      # Frontend: Vercel's GitHub integration deploys automatically on push to main.
      # (Optional CLI deploy: set the VERCEL_TOKEN secret and uncomment the step below.)
      # - run: npx vercel deploy --prod --token=${{ secrets.VERCEL_TOKEN }} --yes

4.8 Problems found while testing the containers, and their fixes

Building and running the stack for real exposed three problems that would also have broken the deployment:

ProblemCauseFix
Frontend image failed: "Cannot find native binding" in npm run buildclient/package-lock.json had been generated on a Mac and listed only the macOS build of the Rolldown bundler (@rolldown/binding-darwin-arm64). On Linux (Docker, GitHub Actions, Vercel) the matching binary was missing (npm bug 4828).Deleted node_modules and the lock file and ran npm install again. The lock file now lists all 16 platform bindings, including linux-x64-gnu and linux-arm64-musl; npm ci and the Docker build now pass.
web container stayed "starting" and never became healthyThe health check used wget http://localhost/. On Alpine localhost resolves to the IPv6 address ::1, but nginx listens only on IPv4.Health checks now use http://127.0.0.1/ (frontend) and http://127.0.0.1:5001/health (API). All three containers report healthy.
http://localhost:8080 returned 403 from another programPort 8080 on the development machine was already used by a Java server, so the browser never reached the frontend container.The host port is now configurable: WEB_PORT in .env (default 8080), also used for CLIENT_ORIGIN. The run below used WEB_PORT=8088.

6. Conclusion

BiteOrder was containerized with Docker: the Node.js API runs from a small non-root image, and the React frontend is built in a multi-stage build and served by nginx. Docker Compose starts MongoDB, the API and the frontend with one command, and all three containers pass their health checks. A GitHub Actions workflow tests the API, builds the frontend, builds both images and triggers the Render deployment, while Vercel deploys the frontend from the same repository. Testing the containers for real also uncovered and fixed three problems (a platform-specific lock file, an IPv6 health-check failure and a port conflict) that would otherwise have failed in CI and in production.
