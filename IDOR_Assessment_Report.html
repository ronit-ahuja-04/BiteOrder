1. Introduction

IDOR (Insecure Direct Object Reference) is a type of Broken Access Control vulnerability. It occurs when an application uses an identifier supplied by a user, such as a profile ID, to access a database record but does not verify whether the logged-in user is allowed to access that record. An attacker may change the identifier in a URL or API request and view or modify another user's private information.

IDOR is important because authentication alone does not guarantee that a user is authorized to access every resource. In BiteOrder, the Profile API uses a MongoDB user ID in the route GET /api/profiles/:id. The test demonstrated that Asha could initially retrieve Bala's profile while using Asha's own JWT. The issue was then prevented by checking resource ownership on the backend before returning profile data. The same test also found, and fixed, an IDOR in the order-details API (section 8.1).

3. Problem Statement

A web application may expose an API endpoint that accepts a resource identifier in its URL. If the backend checks only whether a request contains a valid JWT but does not check whether the authenticated user owns the requested resource, a user can replace the ID in the request with another user's ID. This can expose private profile information.

In the BiteOrder project, the endpoint GET /api/profiles/:id was tested with two accounts: Asha Test and Bala Test. Asha's JWT was kept unchanged while the profile ID in the request was replaced with Bala's MongoDB user ID. The vulnerable API returned Bala's profile with HTTP 200 OK. The API was then secured by comparing req.user.id with req.params.id and returning HTTP 403 Forbidden when the IDs did not match.

4. Theory

1. What is IDOR?

IDOR stands for Insecure Direct Object Reference. It happens when an application exposes a direct reference to an object, such as a user ID, and fails to check whether the requester is allowed to access that object.

2. What is Broken Access Control?

Broken Access Control is a security weakness in which users can perform actions or access data beyond their permissions. IDOR is one example of this weakness. It is ranked number one in the OWASP Top 10.

3. How does IDOR occur?

IDOR can occur when a backend trusts an ID received from a URL, form, or request body without checking ownership or permission. An attacker changes the ID to refer to another user's record.

4. Authentication vs Authorization

Authentication verifies who the user is, commonly through login credentials or a token. Authorization decides what that authenticated user is allowed to access or do.

5. JWT authentication

JSON Web Token (JWT) is a compact token commonly issued after successful login. The client sends the token with later requests, usually in the Authorization header. The backend verifies the token and identifies the user. A valid JWT does not automatically grant access to every user's resources.

6. Express middleware

Express middleware is a function that runs during the request-response process. Authentication middleware can read and verify a JWT, identify the logged-in user, and attach that user's information to the request object.

7. Purpose of req.user.id

req.user.id represents the ID of the authenticated user set by the authentication middleware. It is trusted server-side identity information and can be compared with the requested resource ID to check ownership.

8. MongoDB Mongoose findById()

Mongoose findById(id) searches a MongoDB collection for a document whose _id matches the supplied ID. In this assignment, it is used to retrieve a user's profile. The result should be returned only after authorization checks.

9. Importance of ownership verification

Ownership verification ensures that a user can access only the records they are permitted to access. It prevents users from changing an ID to view another person's private data.

10. HTTP 403 Forbidden

HTTP 403 Forbidden means the server understood the request but refuses to authorize it. In this assignment, the server returns 403 when Asha tries to access Bala's profile. (401 Unauthorized, in contrast, means the request has no valid authentication.)

5.1 Creating two test accounts

Two dummy accounts, Asha Test and Bala Test, were registered in the BiteOrder application through its Register page. Figures 1 and 2 show the account creation forms, and Figures 3 and 6 show the corresponding logged-in profile pages.

5.2 Identifying user IDs

The user IDs were obtained from the profile request and response in the browser Network tab and used as resource identifiers for the API test. Passwords and full JWT values are intentionally not reproduced.

5.3 Implementing the Profile API

The backend exposes GET /api/profiles/:id. The route receives the requested MongoDB user ID as the id route parameter. It retrieves the corresponding user document and returns profile fields while excluding the password field.

5.4 JWT authentication

The Profile API is protected by JWT authentication middleware (protect). The client sends the bearer token in the Authorization header. The middleware verifies the token and attaches the authenticated user's identity to req.user.

5.5 Testing with the API client

GET requests were sent to the local backend endpoint. The Authorization header contained Asha's bearer token. The token was kept the same while the profile ID in the URL was changed for the cross-user access test.

5.6 Demonstrating IDOR before fixing

Asha first requested her own profile and received HTTP 200 OK. Then the URL was changed to Bala's profile ID while Asha's JWT remained in use. The vulnerable API returned Bala's profile with HTTP 200 OK, demonstrating unauthorized access.

5.7 Inspecting vulnerable backend code

The vulnerable route checked authentication but did not compare the authenticated user's ID with the requested profile ID. Therefore, any authenticated user could request another user's profile by changing the ID.

5.8 Implementing ownership verification

The route was updated to compare req.user.id with req.params.id. If the values do not match, the server immediately returns HTTP 403 Forbidden with an access-denied message. The database lookup and profile response are performed only for an owner-authorized request. (Administrators are the only exception, by design.)

5.9 Testing authorized access after fixing

Asha requested her own profile using Asha's JWT and Asha's profile ID. The secure API returned HTTP 200 OK, confirming that legitimate profile access continued to work.

5.10 Testing unauthorized access after fixing

Asha then requested Bala's profile using the same Asha JWT and Bala's profile ID. The secure API returned HTTP 403 Forbidden with the message that the user can access only their own profile.

6.1 User.js – Mongoose User Schema

const mongoose = require('mongoose');
const bcrypt = require('bcryptjs');

const userSchema = new mongoose.Schema(
  {
    name: { type: String, required: [true, '"name" is a required field.'], trim: true, minlength: [2, '"name" must be at least 2 characters.'] },
    email: {
      type: String,
      required: [true, '"email" is a required field.'],
      unique: true,
      lowercase: true,
      trim: true,
      match: [/^\S+@\S+\.\S+$/, '"email" must be a valid email address.'],
    },
    password: {
      type: String,
      required: [true, '"password" is a required field.'],
      minlength: [6, '"password" must be at least 6 characters.'],
      select: false, // never returned by queries unless explicitly requested
    },
    role: { type: String, enum: ['customer', 'admin'], default: 'customer' },
  },
  {
    timestamps: true,
    toJSON: { versionKey: false, transform: (_doc, ret) => { delete ret.password; return ret; } },
  }
);

// Hash the password with bcrypt (10 salt rounds) before saving
userSchema.pre('save', async function () {
  if (!this.isModified('password')) return;
  this.password = await bcrypt.hash(this.password, 10);
});

userSchema.methods.matchPassword = function (plain) {
  return bcrypt.compare(plain, this.password);
};

module.exports = mongoose.model('User', userSchema);

6.2 Authentication Middleware (JWT)

const jwt = require('jsonwebtoken');
const User = require('../models/User');

// protect: verifies the Bearer token and attaches the user to req.user
const protect = async (req, res, next) => {
  const header = req.headers.authorization || '';
  if (!header.startsWith('Bearer ')) {
    return res.status(401).json({ success: false, message: 'Not authorized: no token provided.' });
  }
  try {
    const token = header.split(' ')[1];
    const decoded = jwt.verify(token, process.env.JWT_SECRET); // throws if tampered or expired
    const user = await User.findById(decoded.id);
    if (!user) {
      return res.status(401).json({ success: false, message: 'Not authorized: user no longer exists.' });
    }
    req.user = user;
    next();
  } catch (err) {
    const message = err.name === 'TokenExpiredError' ? 'Not authorized: token expired.' : 'Not authorized: invalid token.';
    res.status(401).json({ success: false, message });
  }
};

6.3 Vulnerable Profile API – Before Fix

// Vulnerable example: authentication is checked, ownership is not.
router.get('/:id', protect, async (req, res) => {
  try {
    const user = await User.findById(req.params.id).select('-password');

    if (!user) {
      return res.status(404).json({ message: 'Profile not found' });
    }

    // IDOR: the requested ID is not checked against req.user.id.
    return res.status(200).json({ profile: user });
  } catch (error) {
    return res.status(500).json({ message: 'Server error', error: error.message });
  }
});

6.4 Secure Profile API – After Fix

const express = require('express');
const router = express.Router();

const User = require('../models/User');
const { protect } = require('../middleware/auth');

// Secure Profile API - IDOR protection
router.get('/:id', protect, async (req, res) => {
  try {
    // Ownership verification: req.user comes from the verified JWT (trusted),
    // req.params.id comes from the URL (untrusted). Admins may view any profile.
    if (req.user.id !== req.params.id && req.user.role !== 'admin') {
      return res.status(403).json({
        message: 'Access denied. You can only access your own profile.',
      });
    }

    // Fetch the profile only after the ownership check passed
    const user = await User.findById(req.params.id).select('-password');

    if (!user) {
      return res.status(404).json({ message: 'Profile not found' });
    }

    return res.status(200).json({ profile: user });
  } catch (error) {
    return res.status(500).json({ message: 'Server error', error: error.message });
  }
});

module.exports = router;

While testing, the same flaw was found in GET /api/orders/:orderId, which returned any customer's order (name, mobile number, items) to any caller, even without a token. 9. Result

The IDOR vulnerability in the BiteOrder Profile API was successfully identified and demonstrated. Result: VULNERABLE before the fix. Before the fix, Asha could access Bala's profile using her own JWT by changing the profile ID. Ownership verification using req.user.id was implemented, after which the API returned 200 OK for Asha's own profile and 403 Forbidden for Bala's profile (NOT VULNERABLE after the fix).

10. Conclusion

This assignment demonstrates that authentication and authorization are both necessary for web application security. A valid JWT confirms the identity of a user, but the backend must also verify whether that user is allowed to access the requested resource. By comparing the authenticated user's ID with the requested profile ID before returning data, the BiteOrder application prevents the tested IDOR vulnerability. Two security measures prevent IDOR: (1) enforce server-side ownership/object-level authorization using the identity from the verified JWT, never an ID supplied by the client, and (2) require authentication on every private route and use unpredictable identifiers instead of sequential ones. Ownership checks should be applied consistently to every private resource and to operations that read, update, or delete user-owned data.
