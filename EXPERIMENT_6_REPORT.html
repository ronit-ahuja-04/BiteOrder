2. Problem Statement

Implement a secure authentication system in the BiteOrder restaurant ordering application (mini project). Integrate authentication with the React frontend and test the functionality using an HTTP client (Postman).

3. Theory Questions

1. What is JWT? Explain its structure and purpose.

A JSON Web Token (JWT) is a compact, URL-safe string used to securely transmit claims between a client and a server. After login the server issues a token; the client sends it with every later request, so the server does not need to keep session state.

Structure: three Base64URL parts separated by dots – Header.Payload.Signature.

• Header: token type and signing algorithm, e.g. {"alg":"HS256","typ":"JWT"}.
• Payload: the claims, e.g. user id, role, issued-at (iat) and expiry (exp). It is encoded, not encrypted, so it must not contain secrets.
• Signature: HMAC-SHA256 of header and payload using the secret key. It proves the token was issued by the server and has not been modified.

2. Differentiate between authentication and authorization.

Authentication answers "Who are you?" – it verifies identity (email and password, then a JWT). Authorization answers "What are you allowed to do?" – it decides which resources the verified user can access (for example, only an admin may create menu items).

Authentication happens first; authorization is applied afterwards using the identity (and role) that authentication established. Failing authentication gives 401; failing authorization gives 403.

3. Why are passwords hashed? What is the purpose of bcrypt?

Passwords are never stored as plain text. If the database leaks, plain-text passwords would expose every account (and other sites where users reuse the password). A hash is a one-way function, so the original password cannot be recovered from it.

bcrypt is a password-hashing algorithm that adds a random salt to each password (so identical passwords produce different hashes) and is deliberately slow with a configurable cost factor (we use 10 salt rounds), which makes brute-force and rainbow-table attacks impractical. bcrypt.compare() checks a login attempt against the stored hash.

4. Explain the purpose of JWT signing and verification.

Signing (jwt.sign) happens at login/registration: the server creates the token and signs header + payload with JWT_SECRET, also setting an expiry (JWT_EXPIRES_IN).

Verification (jwt.verify) happens on each protected request: the server recomputes the signature with the same secret. If the token was tampered with, signed with another key, or has expired, verification throws and the request is rejected with 401. Only the server knows the secret, so clients cannot forge tokens or change their role.

5. What is middleware in Express.js? Explain its role in JWT authentication.

Middleware is a function with the signature (req, res, next) that runs between the incoming request and the final route handler. It can read or modify req/res, end the request, or call next() to pass control on.

In JWT authentication the protect middleware reads the Authorization header, verifies the token, loads the user, attaches it as req.user and calls next(); otherwise it returns 401. The adminOnly middleware then checks req.user.role and returns 403 for non-admins. Routes are protected by chaining them: router.post("/menu", protect, adminOnly, createMenuItem).

6. What is the purpose of Bearer Token in the Authorization header?

The Authorization header carries the credentials for each request in the form Authorization: Bearer <token>. "Bearer" means whoever bears (holds) the token is granted access, so the server only has to verify the token – no username/password is sent again. Because anyone holding the token can use it, it must be sent over HTTPS and kept short-lived.

7. Differentiate between HTTP status codes 401 and 403.

401 Unauthorized – the request has no valid authentication: missing, malformed, invalid or expired token, or wrong login credentials. The client should log in again.

403 Forbidden – the user is authenticated but not permitted to perform the action (for example, a customer calling an admin-only endpoint). Logging in again will not help.

8. What is role-based access control (RBAC)?

RBAC grants permissions according to a user's role rather than to individual users. In BiteOrder each user has a role field – customer or admin. The role is stored in the database and in the JWT; middleware compares it with the role required by the route. This keeps authorization simple to manage: changing a user's role changes everything they can access.

4.2 User model (server/models/User.js)

The schema validates the fields, stores the role (customer or admin), hides the password from query results (select: false) and hashes it in a pre-save hook.

const mongoose = require('mongoose');
const bcrypt = require('bcryptjs');

const userSchema = new mongoose.Schema(
  {
    name: { type: String, required: [true, '"name" is a required field.'], trim: true, minlength: [2, '"name" must be at least 2 characters.'] },
    email: {
      type: String,
      required: [true, '"email" is a required field.'],
      unique: true,
      lowercase: true,
      trim: true,
      match: [/^\S+@\S+\.\S+$/, '"email" must be a valid email address.'],
    },
    password: {
      type: String,
      required: [true, '"password" is a required field.'],
      minlength: [6, '"password" must be at least 6 characters.'],
      select: false, // never returned by queries unless explicitly requested
    },
    role: { type: String, enum: ['customer', 'admin'], default: 'customer' },
  },
  {
    timestamps: true,
    toJSON: { versionKey: false, transform: (_doc, ret) => { delete ret.password; return ret; } },
  }
);

// Hash the password with bcrypt (10 salt rounds) before saving
userSchema.pre('save', async function () {
  if (!this.isModified('password')) return;
  this.password = await bcrypt.hash(this.password, 10);
});

userSchema.methods.matchPassword = function (plain) {
  return bcrypt.compare(plain, this.password);
};

module.exports = mongoose.model('User', userSchema);

4.3 Password hashing and JWT generation (server/controllers/authController.js)

Registration creates the user (the model hashes the password; the role is always "customer", so users cannot make themselves admin). Login compares the password with bcrypt and returns a signed token.

const jwt = require('jsonwebtoken');
const User = require('../models/User');

const signToken = (user) =>
  jwt.sign({ id: user._id, role: user.role }, process.env.JWT_SECRET, {
    expiresIn: process.env.JWT_EXPIRES_IN || '1d',
  });

const sendAuth = (res, status, user, message) =>
  res.status(status).json({ success: true, message, token: signToken(user), user });

// POST /api/auth/register  (role is always "customer"; admins are created via seed script)
exports.register = async (req, res) => {
  try {
    const { name, email, password } = req.body;
    if (await User.findOne({ email: String(email || '').toLowerCase() })) {
      return res.status(409).json({ success: false, message: 'Email is already registered.' });
    }
    const user = await User.create({ name, email, password });
    sendAuth(res, 201, user, 'Registration successful.');
  } catch (error) {
    if (error.name === 'ValidationError') {
      const msgs = Object.values(error.errors).map((e) => e.message).join(' ');
      return res.status(400).json({ success: false, message: `Validation Error: ${msgs}` });
    }
    res.status(500).json({ success: false, message: 'Server error during registration', error: error.message });
  }
};

// POST /api/auth/login
exports.login = async (req, res) => {
  try {
    const { email, password } = req.body;
    if (!email || !password) {
      return res.status(400).json({ success: false, message: 'Email and password are required.' });
    }
    const user = await User.findOne({ email: String(email).toLowerCase() }).select('+password');
    // same message for unknown email and wrong password (no user enumeration)
    if (!user || !(await user.matchPassword(password))) {
      return res.status(401).json({ success: false, message: 'Invalid email or password.' });
    }
    sendAuth(res, 200, user, 'Login successful.');
  } catch (error) {
    res.status(500).json({ success: false, message: 'Server error during login', error: error.message });
  }
};

// GET /api/auth/me  (protected)
exports.getMe = (req, res) => res.status(200).json({ success: true, user: req.user });

// GET /api/auth/users  (admin only)
exports.getUsers = async (req, res) => {
  const users = await User.find().sort({ createdAt: 1 });
  res.status(200).json({ success: true, count: users.length, data: users });
};

4.4 Authentication and authorization middleware (server/middleware/auth.js)

protect verifies the Bearer token and loads the user; adminOnly allows only role = admin.

const jwt = require('jsonwebtoken');
const User = require('../models/User');

// protect: verifies the Bearer token and attaches the user to req.user
const protect = async (req, res, next) => {
  const header = req.headers.authorization || '';
  if (!header.startsWith('Bearer ')) {
    return res.status(401).json({ success: false, message: 'Not authorized: no token provided.' });
  }
  try {
    const token = header.split(' ')[1];
    const decoded = jwt.verify(token, process.env.JWT_SECRET); // throws if tampered or expired
    const user = await User.findById(decoded.id);
    if (!user) {
      return res.status(401).json({ success: false, message: 'Not authorized: user no longer exists.' });
    }
    req.user = user;
    next();
  } catch (err) {
    const message = err.name === 'TokenExpiredError' ? 'Not authorized: token expired.' : 'Not authorized: invalid token.';
    res.status(401).json({ success: false, message });
  }
};

// optionalAuth: attaches req.user when a valid token is sent, otherwise continues as guest
const optionalAuth = async (req, res, next) => {
  const header = req.headers.authorization || '';
  if (header.startsWith('Bearer ')) {
    try {
      const decoded = jwt.verify(header.split(' ')[1], process.env.JWT_SECRET);
      req.user = await User.findById(decoded.id);
    } catch (_) { /* ignore invalid token for guests */ }
  }
  next();
};

// adminOnly: must run after protect; allows only role === 'admin'
const adminOnly = (req, res, next) => {
  if (req.user && req.user.role === 'admin') return next();
  res.status(403).json({ success: false, message: 'Forbidden: admin access required.' });
};

module.exports = { protect, optionalAuth, adminOnly };

4.6 Integration with the React frontend

AuthContext stores the token in localStorage, verifies it on page load with GET /api/auth/me, and exposes login, register, logout and the current user. Other API calls (orders, admin pages, API console) send it as a Bearer header.

import React, { createContext, useContext, useEffect, useState, useCallback } from 'react';

const API = 'http://localhost:5001/api';
const AuthContext = createContext(null);

export const getToken = () => {
  try { return localStorage.getItem('biteorder_token'); } catch { return null; }
};

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(!!getToken()); // true while validating a stored token

  // On page load, verify the stored token with GET /api/auth/me
  useEffect(() => {
    const token = getToken();
    if (!token) return;
    fetch(`${API}/auth/me`, { headers: { Authorization: `Bearer ${token}` } })
      .then((r) => (r.ok ? r.json() : Promise.reject()))
      .then((d) => setUser(d.user))
      .catch(() => localStorage.removeItem('biteorder_token'))
      .finally(() => setLoading(false));
  }, []);

  const authRequest = async (path, body) => {
    const res = await fetch(`${API}/auth/${path}`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(body),
    });
    const data = await res.json();
    if (!res.ok) throw new Error(data.message || 'Request failed');
    localStorage.setItem('biteorder_token', data.token);
    setUser(data.user);
    return data.user;
  };

  const login = (email, password) => authRequest('login', { email, password });
  const register = (name, email, password) => authRequest('register', { name, email, password });
  const logout = useCallback(() => {
    localStorage.removeItem('biteorder_token');
    setUser(null);
  }, []);

  return (
    <AuthContext.Provider value={{ user, loading, login, register, logout, isAdmin: user?.role === 'admin' }}>
      {children}
    </AuthContext.Provider>
  );
}

export const useAuth = () => useContext(AuthContext);

Login/registration pages call these functions (client/src/pages/LoginPage.jsx, RegisterPage.jsx) and the navbar (components/AuthNav.jsx) changes with the login state and role: Login/Register buttons for visitors; user name, role badge and Logout for signed-in users; an extra Admin Dashboard link for admins.

4.7 Protected frontend routes and role-based access

import React from 'react';
import { Navigate, useLocation, Link } from 'react-router-dom';
import { useAuth } from '../context/AuthContext';

// Blocks a page unless logged in (and, if adminOnly, unless role === 'admin')
export default function ProtectedRoute({ children, adminOnly = false }) {
  const { user, loading } = useAuth();
  const location = useLocation();

  if (loading) return <div className="p-10 text-center text-slate-500">Checking session…</div>;
  if (!user) return <Navigate to="/login" replace state={{ from: location.pathname, reason: 'Please log in to access this page.' }} />;
  if (adminOnly && user.role !== 'admin') {
    return (
      <div className="min-h-screen flex items-center justify-center bg-slate-50 p-6">
        <div className="max-w-md w-full bg-white border border-red-200 rounded-2xl p-8 text-center shadow-sm">
          <div className="text-5xl mb-3">🚫</div>
          <h1 className="text-2xl font-black text-slate-900">403 – Access Denied</h1>
          <p className="text-slate-600 mt-2 text-sm">
            This page is restricted to administrators. You are signed in as <strong>{user.name}</strong> ({user.role}).
          </p>
          <Link to="/" className="inline-block mt-5 px-5 py-2.5 rounded-xl bg-[#E8590C] text-white font-bold text-sm">Back to Menu</Link>
        </div>
      </div>
    );
  }
  return children;
}

6. Conclusion

JWT authentication and role-based authorization were added to the BiteOrder application. Users can register and log in; passwords are hashed with bcrypt; the server signs and verifies JWTs with a secret and expiry kept in .env; the protect and adminOnly middleware return 401 for missing or invalid tokens and 403 for insufficient role; and the React frontend uses the token for session handling, role-aware navigation and protected routes.
